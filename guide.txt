1. High-Level Concept

Build a minimalist mining, logistics, and route-optimization game presented as a set of interconnected 2D terrain planes arranged inside a 3D cube.

The player normally edits one 2D plane at a time. However, routes may move between planes through lifts, shafts, transfer nodes, and plane connectors.

The world should feel like a combination of:

Minimalist transit-network routing
Spatial puzzle solving
Light mining automation
Factory logistics
Permanent, continuously expanding infrastructure
A layered 3D topology viewed through readable 2D slices

The main challenge is not building the largest factory. It is designing the most efficient network through constrained three-dimensional terrain.

The player must determine:

Which plane each resource should travel through
Where to cross between planes
Which routes should share infrastructure
Whether a direct route is worth its construction cost
How to avoid congestion and conflicting crossings
Where processing should occur
Whether material should be refined near its source or transported raw
How to reserve space for future expansion

The world expands indefinitely outward and downward.

2. Core Player Fantasy

The player is designing an enormous subterranean transport lattice.

A successful network should feel:

Elegant
Organized
Geometrically satisfying
Efficient
Easy to understand at a glance
Increasingly impressive as it grows

The player should regularly experience moments such as:

“This resource cannot reach the refinery on this plane, but I can move it two planes backward, route beneath the water pocket, transfer sideways, then return to the refinery plane.”

The joy comes from discovering clean spatial solutions.

3. Core Design Pillars
3.1 Route Optimization First

The central activity is creating efficient paths between:

Resource deposits
Extractors
Transfer stations
Processing facilities
Storage hubs
Delivery objectives

Factories and automation support the routing puzzle rather than replacing it.

A machine should matter because of where it must be connected, not because the player needs to manage hundreds of recipes.

3.2 Understandable Three-Dimensionality

The world is three-dimensional, but the player edits readable 2D slices.

Never require the player to manipulate a confusing free-camera 3D factory for routine construction.

Provide three main views:

Plane View
A single editable 2D cross-section.
Ghosted Neighbor View
The active plane with nearby planes faintly visible.
Matrix Overview
A rotatable or fixed isometric visualization of every plane and route.
3.3 Beautiful Minimalism

The terrain should use:

Soft pastel colors
Rounded geometry
Subtle slopes
Clean visual hierarchy
Low visual noise
Gentle gradients
Small ambient animations

The world should look handcrafted even though it is procedurally generated.

3.4 Permanent Expansion

This is not a sequence of disposable puzzle maps.

The player owns one persistent network that expands through new sectors.

New regions introduce:

New resources
New geological constraints
New route restrictions
New production demands
New cross-plane dependencies
3.5 Optimization Without Mandatory Perfection

The game should reward better solutions without forcing a single correct answer.

Players may create:

A cheap but slow network
A reliable redundant network
A highly optimized compact network
A complex high-throughput network
4. World Representation

Represent the underground world as a sparse three-dimensional grid of sectors.

World
 ├── X axis: horizontal expansion
 ├── Y axis: depth
 └── Z axis: plane position

However, divide the Z axis into named plane slices.

Example:

B4 B3 B2 B1 CURRENT F1 F2 F3 F4 F5

The player may also move through side-plane groups:

S1 through S10

A practical internal coordinate may be:

Vector3i cell = (x, y, z)

Each visible 2D plane edits two dimensions while holding the third constant.

For example:

Front plane view:
x = horizontal position
y = depth
z = selected plane

The “side-plane” system can initially be represented as a second slicing orientation over the same voxel grid rather than a literal fourth spatial dimension.

Recommended implementation:

Use one true 3D integer grid
Support viewing slices along either the X or Z axis
The normal front view fixes Z
The side view fixes X
Both views modify the same underlying world

This produces actual three-dimensional problem solving without creating a four-dimensional data structure.

13. Efficiency Scoring

The player should receive useful feedback but not be forced into one solution.

Track:

Average delivery time
Total route length
Material throughput
Congestion
Power efficiency
Number of transfer points
Construction cost
Route overlap
Idle machine time
Deadhead travel
Network resilience
Unused capacity
Pollution
Excavated volume

Possible score formula:

Network Efficiency =
Delivered Value
/
(
Travel Cost
+ Power Cost
+ Congestion Penalty
+ Transfer Penalty
+ Construction Amortization
)

Use normalized values rather than raw units.

Example:

efficiency =
    delivered_units * average_delivery_value
    / max(
        1,
        total_route_distance * 0.2
        + energy_used * 0.3
        + average_delay * 0.4
        + transfer_count * 2.0
    )

Do not expose the entire mathematical formula by default. Present understandable diagnostics:

“Copper spends 38% of its journey waiting.”
“This lift operates at 96% capacity.”
“Moving the smelter closer would reduce route length by 22%.”
“The F2 plane has unused tunnel capacity.”
14. Vehicle and Cargo Simulation

Do not simulate every wheel or physics interaction.

Use graph-based movement.

Each route network is a graph:

Node:
Junction, building port, transfer point, lift, connector

Edge:
Tunnel, conveyor, pipe, cross-plane segment

Vehicles and cargo move along graph edges.

RouteNode
{
    NodeId id;
    Vector3Int worldPosition;
    NodeType type;
    List<EdgeId> edges;
}

RouteEdge
{
    EdgeId id;
    NodeId start;
    NodeId end;

    RouteType routeType;
    float length;
    float capacity;
    float speed;
    float congestion;
    bool oneWay;
}

Pathfinding should initially use A* or Dijkstra.

Edge cost:

edge_cost =
    travel_time
    + congestion_penalty
    + transfer_penalty
    + hazard_penalty

For repeated freight paths, cache route results until topology changes.

15. Congestion

Congestion is important because it turns route drawing into an optimization problem.

Every edge has:

Maximum occupancy
Maximum throughput per second
Current queue
Speed multiplier

Example:

load_ratio = current_occupancy / max_occupancy

if load_ratio <= 0.7:
    speed_multiplier = 1.0
else:
    speed_multiplier = lerp(1.0, 0.25, inverse_lerp(0.7, 1.4, load_ratio))

Junctions should also have capacity.

A route can therefore be short but inefficient because too many networks share one junction.

19. Procedural Terrain Pipeline

Use a multi-stage terrain generator.

Stage 1: Base Density Field

Generate continuous terrain density with layered noise.

density =
    base_depth_gradient
    + large_scale_noise * 0.55
    + medium_noise * 0.25
    + fine_noise * 0.08
    + geological_band_offset

Recommended conceptual noise layers:

Large noise for broad terrain shapes
Medium noise for hills and caverns
Fine noise for subtle variation
Directional noise for geological strata

Use OpenSimplex, simplex noise, or equivalent coherent noise.

Stage 2: Geological Bands

Create depth-dependent material bands.

band_value =
    y
    + noise(x * 0.015, z * 0.015) * band_warp

Assign rock types based on thresholds.

Do not use perfectly horizontal layers. Warp them gently.

Example:

warped_depth =
    world_y
    + noise(world_x * 0.02, world_z * 0.02) * 12
Stage 3: Caverns

Create caves using a separate density field.

cave_noise =
    abs(noise3D(x * cave_scale, y * cave_scale, z * cave_scale))

is_cave = cave_noise < cave_threshold

Combine this with seeded spline caverns so important regions remain navigable.

Stage 4: Puzzle Constraints

After natural terrain generation, intentionally place puzzle structures:

Barrier wall
Aquifer
Hazard band
Restricted zone
Resource basin
Required connection corridor

These should be authored by procedural templates, not left entirely to random noise.

Stage 5: Resource Placement

Resources should follow geological logic.

Examples:

Oil appears in sedimentary pockets
Gold appears in narrow veins
Salt appears in broad layered deposits
Uranium appears deep and near granite
Water gathers in cavities and aquifers
Copper appears in clustered veins
Iron appears in larger common deposits
Stage 6: Visual Smoothing

Convert the blocky simulation boundary to smooth visual geometry.

Possible methods:

Marching Squares for each 2D slice
Marching Cubes for the matrix overview
Signed distance field contouring
Bezier smoothing over extracted contours
Polygon triangulation with rounded corners

For the normal plane view, Marching Squares is sufficient.

20. Beautiful 2D Terrain Geometry

The visible plane should not appear as a square tile map.

Generate a scalar density field around the logical cells.

Then extract terrain contours.

for each render sample:
    density = sample_logical_terrain_with_interpolation()

contours = marching_squares(density, threshold = 0.5)
smoothed_contours = chaikin_smooth(contours, iterations = 2)
mesh = triangulate(smoothed_contours)

Use a denser render grid than the gameplay grid.

Example:

Gameplay grid:
1 logical cell

Render field:
4x4 or 8x8 samples per logical cell

This allows tunnels and caverns to have subtle organic curves.

Tunnel Smoothing

When a tunnel is excavated:

Mark logical cells as open.
Add a rounded capsule-shaped subtraction to the visual density field.
Blend neighboring excavations.
Regenerate only the affected terrain chunk.

For a path segment between points A and B:

distance_to_segment = distance(sample_position, segment(A, B))
tunnel_density_subtraction =
    smoothstep(tunnel_radius, tunnel_radius - softness, distance_to_segment)

This creates beautiful rounded tunnel walls.

26. Procedural Puzzle Validation

Before presenting a generated region:

Build a simplified traversability graph.
Place required sources and destinations.
Run pathfinding under construction restrictions.
Confirm at least one valid solution.
Estimate the best possible route cost.
Reject trivial or impossible layouts.
Prefer layouts with several meaningfully different solutions.

Pseudo-process:

for attempt in 1..MAX_ATTEMPTS:
    region = generate_region(seed + attempt)
    graph = build_candidate_construction_graph(region)

    solutions = find_k_reasonable_paths(graph, source, destination, k = 4)

    if solutions.count >= 2
       and solutions[0].cost > minimum_complexity
       and solutions[0].cost < maximum_complexity:
        accept(region)

Sprite Processing

The neon pink background should be removed during asset import.

Use a chroma-key shader or preprocessing script.

Recommended preprocessing:

for each pixel:
    if color_distance(pixel.rgb, neon_pink) < threshold:
        pixel.alpha = 0

Use a small edge-spill correction to prevent pink halos.

if alpha is partially transparent:
    replace pink-contaminated RGB with nearest opaque neighbor color

Then:

Trim transparent margins
Preserve consistent pivot points
Create metadata files
Group sprites by category
Generate thumbnails
Use nearest or linear filtering based on source quality

Because the sprites are painterly and smooth rather than strict pixel art, use bilinear filtering.

64–96 px

40. Engine Recommendation

Godot is a strong choice for an AI-assisted implementation because:

Good 2D tools
Accessible procedural mesh APIs
Resource-based data architecture
Easy custom editor tooling
Good support for shaders and splines
Lightweight project structure

Unity is also suitable, particularly if the developer already prefers C#.

For a first implementation, use:

2D plane scenes
A logical 3D grid
A separate 3D overview scene
Procedurally generated 2D terrain meshes
Graph-based cargo movement

Do not begin by building the entire game as a fully 3D voxel world.

43. Performance Strategy

Do not update every vehicle and machine every frame.

Use:

Fixed simulation ticks
Route-level aggregate flow for distant networks
Object pooling
Chunk culling
Cached pathfinding
Dirty-region graph rebuilding
Simplified matrix-view rendering
Lower-frequency updates for offscreen planes

Example:

Visible active plane:
Full vehicle animation

Neighboring planes:
Reduced animation rate

Distant planes:
Aggregate throughput simulation only

46. AI Coding Rules

The coding LLM should follow these rules:

Build small working systems before adding content.
Keep all resource and machine definitions data-driven.
Do not hardcode individual resources into route logic.
Keep terrain simulation separate from terrain rendering.
Keep route graph simulation separate from sprite animation.
Write deterministic generation tests.
Add debug visualization for every procedural system.
Add route graph inspection tools.
Add a button to regenerate the current puzzle region.
Add a button to visualize pathfinding costs.
Avoid premature multiplayer support.
Avoid realistic physics for carts.
Avoid full voxel rendering in the normal plane view.
Preserve save compatibility through versioned data.

50. Final Product Identity

The finished game should not feel like a factory simulator with multiple floors.

It should feel like a spatial network puzzle taking place inside a living underground cube.

The defining question should always be:

“What is the cleanest way to move these resources through this three-dimensional terrain?”

Factories, miners, vehicles, resources, and power systems exist to create interesting routing demands.

The route network is the real machine.
